## 案例 1：29% 空答案——把"模型不行"误判成"协议问题"

**现象。** 第一版端到端评测跑 MuSiQue 103 题：EM 0.107 / F1 0.174 / 证据召回 0.607@10，
但**29% 的题答案是空字符串**、42% 答 unknown。baseline 低到没法用，第一反应是"模型太弱"。

**根因。** 看遥测才发现：空答案里 28/29 是 `completion_tokens` 撞上限、`finish_reason=length`。
这个模型带思维链，推理与最终答案**共用 completion 预算**——预算 512 时推理把额度用光，
答案一个字都出不来。提到 1024 仍不够，个别题 4096 还在"反复复核"式打转。
这跟模型能力没关系，是生成协议缺陷。

**修复。** 三件事一起改：

1. CLIent 遥测补 `finish_reason` 与 `reasoning_tokens`（没有这两个字段时，空答案和答错分不开）；
2. 答案预算首轮 1024，空答案带**收尾提示**（"禁止复核、≤5 词、不知道就答 unknown"）
   按 2048→4096 阶梯重试（v2 单次重试残留空答 8.9%，v3 阶梯降到 ~1%）；
3. 评测行落 `n_calls` / `finish_reasons` / `answer_empty`，汇总表加空答率与重试率两列。

**回归。** `tests/test_agent.py` 里有 4 条专测这条路径：空答案触发重试、阶梯逐级升预算、
全部失败后如实留空并打标记、非空答案不触发重试。任何"顺手把预算调回 512"的优化都会让它们红。

**结果。** 同口径 50 题下 naive 行 EM 0.267（103 题旧口径）→ 0.300、F1 0.422、空答率约 1–3%。
现在这一行是整张消融表的锚（`decisions/D1`）。

**90 秒口述。** 我的 baseline 一开始只有 EM 0.107，29% 的题答案为空。我以为是模型不行，
但看了自己记的 `finish_reason` 才发现空答案全是 `length`——这个模型带思维链，推理和答案共用
token 预算，512 的预算全被推理吃掉。所以我改的不是提示词而是生成协议：首轮 1024，
空答案带着"禁止复核、五个词以内"的收尾提示逐级加预算重试，同时把 `finish_reason` 和空答率
写进评测行。空答率从 29% 降到 1% 左右，同口径 EM 从 0.267 提到 0.300。这个案例的教训是：
**指标异常先查测量与协议，再怀疑模型**；而能查到，是因为遥测里记了那个字段。

## 案例 2：批准的 3,815 块，跑了 20,287 块——参数化漏改硬编码导致超支 ~946 万 token

**现象。** 实体抽取（付费 LLM 步骤）本来只批了小库 3,815 块的预算，跑完对账发现累计
23,876 次调用 / 11,136,779 token，其中**超支约 946 万 token**。

**根因。** `build_kg.py` 加变体参数（samples / full_dev 隔离）时，改的是命令行参数与输出目录，
**漏改了读语料那一行的硬编码路径**——于是"小库任务"实际读了全库语料。
产物目录名是小库的，语料却是全库的。

**修复。**

1. 语料读取彻底 variant 化，路径由同一个变体参数推导，不再有第二处硬编码；
2. NER 缓存解析改为按语料过滤（此前按行号对齐，语料一变就错位）；
3. finalize 阶段按语料块集合过滤，**产物与语料的一致性靠代码过滤，而不是靠目录命名约定**；
4. 立流程规矩：批量 API 任务先报预估花费、经确认再启动（此前有一条"价格不设限"的旧记录，作废）。

**回归。** 小库目录按 4,646 块重建；全库那次零失败抽取归档为 `full_dev` 留作备用。
诚实说：**这条没有自动化测试兜住**，靠的是流程规矩 + 产物指纹。
（现在的 M3 里已经有 `eval/manifest.py` 记录语料块数与块 id 指纹，同类错位会被指纹发现。）

**结果。** 事故反而把"全量建图"的 API 部分意外做完了（16.5 万节点全库图），
小库重建后 ③ 行顺利出数；三处 bug 修完一并进了 commit `f0867a5`。

**90 秒口述。** 有一次付费抽取我批准的是 3,815 块，实际花了 946 万 token 的超支。原因很蠢：
加了变体参数，改的是参数和输出目录，漏改了读语料那一行的硬编码，于是"小库任务"跑了全库。
修的时候我没有只改那一行，而是把语料、NER 缓存、finalize 过滤三处都改成由同一个变体推导，
并且立了"批量 API 先报预算"的规矩。后来我把语料块数与 id 指纹写进了 run manifest——
同样的错位现在会被指纹直接暴露。

## 案例 3：三套融合策略全无增益——把负结果留下，而不是藏掉

**现象。** ③ 号位置（第三路检索信号）最初做的是 wiki 条目索引：加权 RRF、条目先验、
准入补捞三种融合方式都试了，**没有一种带来正增益**；甚至做了 oracle 上限分析，仍不成立。

**根因。** wiki 视图是"同编码器信号的粗化"——它和 dense 用的是同一个编码器，
只是粒度更粗（条目层 vs 块层）。融合时它带来的是**相关性而非新信息**，
任何加权都会稀释 dense 的排序，而不是补上缺失的证据。

**修复。** 不是修 bug，是**换信号**：改用 LLM 抽取的实体关系图 + 图上 PPR 游走。
它和 BM25/dense 的错误不相关（实体图能跨文档连共享实体），单路 full_hit 0.503 已超过 hybrid，
等权融合后 recall@20 +7.2pp、full_hit@20 +13.3pp（45 胜 5 负）。

**回归。** `configs/ablation/plus_wiki.yaml` 与 `use_wiki` 开关**故意保留**——
负结果要能复现，不然下次还会有人再试一遍。代码注释里写清"已实测无净增益"。

**结果。** ④ 号位置（wiki）在收官时裁撤入档；③ 号位置换成实体图，成为消融表里
唯一提升证据覆盖的行（证据召回 0.720→0.813）。

**90 秒口述。** 我试过把 wiki 条目索引当第三路检索，加权、先验、补捞三种融合都做了，
全都没有正增益，连 oracle 上限都试了还是不行。分析下来它和 dense 是同一个编码器的粗化版本，
提供的是相关性不是新信息，加权只会稀释。所以我没把它硬塞进主线，而是换了信号：
LLM 抽取的实体关系图加图上游走，它的错误和 BM25/dense 不相关，等权融合就带来了
+7.2pp 召回、+13.3pp full-hit。但那个开关我一直留着，让负结果可以被复现——
面试里我更愿意讲"我怎么否决了自己一个方向"，而不是只讲成功的那条。

## 选材说明（为什么是这三个）

- **协议类**（案例 1）：证明"指标异常先查测量"，以及遥测字段的用途；
- **成本/流程类**（案例 2）：证明会为付费步骤设预算、会把一致性写成代码；
- **判断类**（案例 3）：证明会杀掉自己的方向，且把负结果留成可复现证据。

三个案例分别对应岗位最常追问的三件事：**效果从哪来、钱花在哪、什么不该做**。

## 案例 4：加了证据核验，EM 反而掉了 2 题——负结果怎么处置

**现象。** 在全家桶配置上再叠一层"claim 核验 + 有限修复"（`plus_verify`），同题集 50 题：
EM 从 0.460 掉到 0.420（−2 题），F1 基本持平（0.599 → 0.604），token 从 11,834 涨到 20,087（**+70%**）。
功能明显"没赚"，第一反应是删掉。

**根因（逐题拆开才看清）。** 三件事同时发生：

1. **拒答是诚实的**：6 题被改成 `unknown`，其中 **5 题原本就是错的**——拒答不亏，反而更可信；只有 1 题本来答对。
2. **修复确实在起作用，但成功率有限**：触发修复 10 次，成功 4 次（40%）。
3. **EM 掉分主要来自答案变长**：修复后重答的答案带上了限定语——`661` → `661 CE`、`2013` → `2013 (Silver)`、`c. 1000 BCE` → `c. 1000 BCE (according to …)`。EM 是字符串精确匹配，多一个括号就判错。
   这和前面"答案风格漂移"是同一个根因（`decisions/D7`），只是这次是**我们的修复流程鼓励模型多说一点**。

**后续更正（重要）。** 后来补了"宽松 EM"诊断口径（金标 token 集合被预测包含即算命中，见 `decisions/D10`）重算：全家桶 30/50、核验行 **32/50**——**核验层在宽松口径下是赢的（+4/−2），严格口径下才是输的（+4/−6）**。所以"核验没用"这个结论是口径造成的，不是机制无效；真正的结论是"它让答案更完整，而严格 EM 惩罚完整性"。这一段保留原判读，是为了留下"我怎么发现自己判错了"的过程。

**处置。** 没有删功能，而是把它重新定位并如实记录：

- 这一层买到的不是 EM，是 **claim support rate 0.885** 和"6 题拒答里 5 题合理"——属于**可信度**而非**效果**；
- 报告里把它单列一行并标注成本，不并入主线结论；
- 真要让它在 EM 上有收益，得先做**答案规范化或软匹配**（或在 answer 提示里加硬性词数上限），那是另一个实验。

**回归。** `tests/test_diagnosis.py` 18 条覆盖解析/引用校验/五分类/修复上限/拒答/预算；`tests/test_agent_graph.py` 覆盖核验修复在 graph 与顺序两条路径上的一致。

**90 秒口述。** 我给 Agent 加了一层证据核验：答案拆成 claims，引用编号由代码校验，没支撑就补检索一次，还不行就拒答。结果 EM 反而掉了 2 题、token 涨 70%。逐题拆开发现三件事：6 题改成拒答里 5 题本来就是错的，修复触发 10 次成功 4 次，而掉分主要来自重答时答案变长——`661` 变成 `661 CE`，精确匹配就判错了。所以我没删它，而是把它从"提分模块"重新定位成"可信度模块"：它赚的是 claim support 0.885 和诚实拒答，不是 EM。要真提分，得先解决答案规范化，这是下一个实验。
