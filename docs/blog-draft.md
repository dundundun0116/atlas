## 1. 引子：long-horizon 任务的两个杀手

让 agent 跑一个几百步、跨多个会话、子任务环环相扣的长任务，你会撞上两堵墙：

1. **上下文窗口有限**——历史必须压缩，这是绕不开的；
2. **压缩丢状态**——摘要丢掉精确值，检索丢掉依赖链，于是 agent 违反早期约束、重复犯已修正的错误、目标漂移。

我在 MemoryArena 基准（701 个多会话相互依赖任务）上看到的数字很能说明问题：现有记忆系统——包括 Mem0、GraphRAG 这类明星项目——任务全对率最高约 29%；2D 结构化记忆最好的约 17%；所有方法随子任务深度全线衰减。有的系统甚至不如**不压缩、全历史硬塞**的基线。

这两类方案各有各的失败方式：

- **总结式压缩**：LLM 把历史压成一段散文。结构没了、数值被四舍五入、约束被顺手省略。
- **语义检索式记忆**：把记忆拆成条目、嵌入向量库，用的时候按相似度捞。可相互依赖的任务里，"第 3 步依赖第 1 步的结论"不是语义相似度能表达的关系——状态被打碎（state fragmentation），捞回来的是碎片，不是链。

结论：执行状态（目标、约束、决定、产出物、环境事实）需要一个**既不依赖语义相似度、也不依赖自由文本摘要**的结构化承载。这就是我做 Atlas 的起点。

## 2. Atlas 的三个工作点

一句话：**以带时效的图状态记忆承载执行状态，以结转式上下文管理衔接状态层与模型上下文，多智能体围绕共享状态图协作。**

### 2.1 图状态记忆

节点六类：Goal / Subtask / Constraint / Decision / Artifact / Fact。关键设计有两条：

- **时效而非删除**：节点有 status 生命周期（active → superseded / expired），被推翻的节点不删除，而是打上 superseded_by 边、留时间戳。图永远能回答"当时为什么这么决定"。
- **决策变迁**：Decision 节点带 reason 和 evidence。"住西湖区"被推翻为"住滨江区"时，旧决定还在图里，推翻原因（展会期间房价翻倍，超预算）也在——读取端只取 active 节点，历史随手可查。

### 2.2 结转式上下文管理

结转（carry-over）替换了总结式压缩：**在压缩历史之前，先把结构化状态提取进图**；上下文由组装器从图重新生成，而不是从被压缩的散文里猜。具体是每子任务边界触发一次：LLM 提取器从刚结束的会话段里抽出 Fact / Constraint / Decision / Artifact（含 supersede 作废更新），严格 JSON 落图；然后组装器按四区拼装下一步的上下文——计划/约束区（从图生成）、图摘要 C、近期原始记录 R、提示 H——各区预算动态适配，总预算 8k tokens（对比基线全篇 10–25k）。

一道便宜的保险：**规则式结构查账**——活跃的 Constraint / Decision 节点如果在组装结果里缺席，直接报错降级，零 LLM 成本。

### 2.3 多智能体编排

三段式：Planner 定路线（写 Decision）→ Worker 解题（写 Artifact 草稿）→ Auditor 核验（写 Fact 疑虑）→ 仅当 Auditor 判"需修订"时 Worker 修订一次（修订稿作废草稿、记原因）。所有协调**经由共享图而非对话**：角色结论经 role_note 落成图节点，下一角色读图状态视图继续，没有任何"把聊天记录传给下一个 agent"的动作。

## 3. 实现踩坑（这部分最值钱）

### 3.1 推理模型把预算全花在"思考"上

跑分抓到的第一只虫：agent 的答案偶尔是**空的**。排查发现是推理型模型把 max_tokens 预算几乎全部花在思考（reasoning tokens）上，正文没生成就被截断。同一机制以另一种形式咬了我们第二次：结转提取器让模型输出严格 JSON，长记录段上 deepseek-v4.1-flash 推理失控——8000 token 预算全被思考吃光，单次调用 17 分钟，常以连接错误告终。

修复组合拳：max_tokens 提到 32000；空正文检测 + 重试；以及下面的选型。

### 3.2 机械性调用要关推理、用小模型

端点实测支持 `thinking.type=disabled`。提取器换成 mimo-v2.6-flash + 关推理之后：**17 分钟 → 33 秒**，推理 token 归零，JSON 还合规。编排里的机械调用（Planner、Auditor 的 JSON 输出）一律关推理；解题调用（Worker）保持推理。一个数量级的提速，来自把"哪些调用不需要思考"想清楚。

### 3.3 基础设施三连

- **代理误伤本地服务**：shell 继承的 HTTP_PROXY 指向 Clash，而本地 memory server 地址不在 NO_PROXY 里，对 127.0.0.1 的请求被误发进代理——Clash 一抖，跑分全报 ProxyError。修复是补 no_proxy 名单；教训是"本地地址"四个字要逐个协议核对（0.0.0.0 ≠ localhost ≠ 127.0.0.1）。
- **HF datasets 的缓存回退 bug**：hub 偶发失败时 datasets 走的回退路径会把 split 拼进 config 名，直接 ValueError。本地缓存直载优先，完全绕开 hub。
- **runner 的隐藏噪声**：官方 runner 在首个 wrap 前会先 add 一条 "Initial result: Empty"，不认识它会把它当成待结转的记录，白烧一次提取调用。

### 3.4 TDD 在 LLM 项目里依然成立

图引擎、组装器、提取器解析、服务分派全程 TDD（86 个测试）。测试抓到过两个纯逻辑 bug（决策链回溯方向反了；Fact/Artifact 在组装结果里没有出口）。LLM 的不确定性不可测，但**围绕它的解析、校验、降级路径**完全可测，也最值得测。

## 4. 评测设计

- **基准**：MemoryArena math 域（formal reasoning），一篇论文 = 一个记忆会话，子任务相互依赖（后面的题用前面推的结论）。
- **协议**：官方 runner + 固定抽样子集（n=10、固定种子），报成绩注明抽样口径。
- **三臂对照**：`long_context`（官方基线，全历史硬塞）vs `atlas`（图状态记忆）vs `atlas_orch`（+ 编排）；判分口径两臂一致（judge_result_in_memory=true）。
- **编排评估**：编排开关 A/B + 角色消融 + 成本核算。

## 6. 复盘

- 把"执行状态"当成一等公民建模（图 + 时效 + 决策变迁），比把它埋进散文摘要或在向量库里捞碎片，在相互依赖任务上更稳——待主评测数字验证。
- 上下文管理是状态层与模型上下文之间的**通道**，不是压缩算法：先结转入图、再由图组装，压缩才不丢结构。
- 多智能体的价值不在"多个脑子"，而在角色分工让每次调用的职责单一——这正是"哪些调用可以关推理"的前提，也是成本可控的前提。
- 工程上最大的教训：LLM 应用的失败大多不在模型能力，而在预算分配（max_tokens 被思考吃光）、基础设施（代理/缓存）和协议细节（judge 口径、隐藏噪声）。
