## 一 项目定位和介绍边界

### 一句话定位

我做的是 Atlas，一个可恢复、可核验的研究型 RAG Agent。它把资料检索、答案生成、证据核验和执行状态保存串起来，让多步骤研究过程有来源可查，中断后也有依据判断从哪里继续。

### 项目的三个重点

第一，获取证据。Retriever Tool 使用关键词检索、可选语义检索和排名融合，也提供查询改写、多跳和实体图等实验能力。

第二，检查证据如何被使用。检索结果带来源、chunk 标识和原文片段；生成后可以进行 claim 核验，研究流程还有草稿审核和终检。

第三，保存执行状态。研究步骤、依赖、尝试记录和工具结果进入数据库；遇到中断或未知调用结果，先判断恢复条件，再推进任务。

这三个重点有先后关系：先用 RAG 提供研究依据，再用核验减少没有依据的结论，最后用运行时保存过程。图记忆、上下文组装和角色分工都服务于这条主线。

### 当前可以说和应当避免的说法

| 主题 | 可以直接介绍 | 应当避免的表述 |
|---|---|---|
| 任务规划 | 固定研究模板生成显式 DAG，支持校验、依赖绑定和逐步执行 | 自动拆解并解决任意复杂研究任务 |
| 检索 | BM25 和可选 BGE M3 稠密检索，通过 RRF 融合 | 已部署海量向量数据库或 HNSW 服务 |
| 图结构 | 执行 DAG、研究状态图和检索实体图各有职责 | 所有图都是同一张 GraphRAG 知识图谱 |
| 核验 | 有独立 claim 核验和研究审核阶段，启用方式及降级策略各不相同 | 所有回答都通过严格事实核验，能够消除幻觉 |
| 持久化 | 保存步骤、结果、事件和 checkpoint，覆盖若干明确恢复场景 | 任意崩溃点都能无损恢复，完整数据库均可由事件重建 |
| 幂等 | 持久化 ToolCall 有稳定键和唯一约束，多个入口的保障不同 | 系统所有请求都具备跨进程端到端 exactly once |
| 效果 | 机制测试、固定题集实验和小样本真实模型结果分别解释 | 用脚本化测试通过率证明模型理解能力或业务收益 |

## 二 以面试者身份完整介绍项目

### 版本一 一分钟介绍

我做的项目叫 Atlas，定位是可恢复、可核验的研究型 RAG Agent。

我关注的是普通 RAG 在多步骤研究任务里的几个问题：检索到了相关段落，不代表答案有依据；查了几轮以后，证据和中间结论容易混在一起；模型或工具调用中断后，也很难判断该重做还是继续。

所以我把系统分成两层。检索层负责 BM25、语义检索和 RRF 融合，返回带来源的证据；Atlas 负责把检索、草稿、核验和修订组织成持久化步骤，保存每一步的输入、输出和调用记录。

项目里我最重视两个点：一是区分引用是否合法和证据是否支持结论，分别由代码和模型处理；二是区分调用失败和结果未知，超时后先查明原调用结果，避免盲目重发。当前主要完成的是固定研究工作流和相关可靠性机制，效果评估也区分检索指标、模型作答质量与故障恢复能力。

### 版本二 五分钟完整介绍

我想介绍的项目是 Atlas，一个可恢复、可核验的研究型 RAG Agent。

这个项目最初关注长任务中的记忆和上下文管理，后来加入了检索、执行状态和恢复机制。我整理之后，把它收敛到一个更明确的场景：一个问题需要经过查资料、形成草稿、核对依据和必要修订，系统要能解释答案从哪里来，以及任务为什么停在某一步。

普通 RAG 的基本链路是检索加生成。它解决了模型访问外部资料的问题，但仍有几个工程缺口。第一，相关段落不一定包含回答所需的完整证据，尤其是多跳问题。第二，模型即使拿到了证据，也可能生成材料里没有的结论。第三，多步骤执行时，如果只是把所有东西放在聊天历史里，证据、草稿、旧决定和失败记录会混在一起。第四，工具超时或者进程退出之后，程序很难区分哪些步骤已经完成、哪些调用结果仍然未知。

因此我把系统分成检索工具和研究运行时两层。检索工具保留在 compassrag 包中，Atlas 调用它的 ResearchTool 协议。检索工具返回答案、证据片段、来源、chunk 标识和 trace，而不决定整个研究任务是否完成。Atlas 才负责步骤推进、上下文、持久化和恢复。

检索层的基础是 BM25 和稠密检索。BM25 用于实体名、术语和精确关键词，稠密检索用于语义表达不同但内容相关的情况。稠密模型采用 BGE M3，本地实现是归一化向量矩阵的点积检索，没有使用向量数据库。我通过 RRF 融合不同检索器的排名，避免直接比较 BM25 分数和余弦相似度。查询改写、多跳决策和实体图是可配置的增强能力，我会通过消融判断它们是否值得增加成本，而不是默认全部打开。

在证据层，我保留文档来源、chunk 标识、原文片段和检索轨迹。启用 claim verifier 时，模型把答案拆成 claims，并提出证据编号；代码负责检查引用是否为空、编号是否越界，以及引用是否属于这次候选集合。这里我特别区分结构合法和语义支持：编号正确不代表事实正确，语义支持仍然是模型判断。当前核验解析失败会留降级标记，并不是所有情况下都强制拒答，所以我把它称为核验机制，而不是事实正确性保证。

Atlas 的主研究流程采用显式 DAG：检索、草稿、审核、可选修订和终检。当前是确定性的研究模板，不是让模型随意生成通用工作流。每个 Step 有输出、输入绑定和完成判据，模型输出先作为候选结果，再交给程序判定是否满足步骤条件。检索证据不只传给草稿，也传给审核和终检，避免审核者只有答案却看不到原始依据。修订没有问题清单时直接复用草稿，减少额外调用。

持久化部分使用 SQLAlchemy 和 SQLite。执行步骤与知识状态分开保存：计划、依赖、Step、Attempt 和 ToolCall 表保存执行情况，状态图保存目标、约束、决定、事实和产出。需要说明的是，当前 DAG 的检索证据主要保存在工具结果和步骤输出中，并不自动全部写成 Fact；旧编排和独立研究接口才有相应的 Fact 入图路径。这样介绍比把所有功能拼成一个理想流程更准确。

可靠性是另一条重点。外部调用前先记录调用意图，成功结果可以被后续恢复复用。如果请求发出后超时，系统不会简单认为上游没有执行，而是把结果标记为未知，先对账或交由人工确认。恢复时检查持久化步骤和在途调用，只继续符合条件的未完成工作。现在覆盖的是若干明确中断场景，还不能保证任意运行阶段崩溃都能自动接管。

在验证上，我把三件事分开。检索层看证据召回、完整支持证据命中和答案 EM 或 F1；核验层看支持率、拒答、误拒答和额外成本；运行时看故障是否真的触发、恢复是否成功、是否产生重复调用和状态残留。脚本化测试证明规则和机制，小样本真实模型实验提供初步效果证据，两者不混用。

这个项目让我最明确的一点是：一个研究 Agent 的可靠性来自不同组件的职责边界。检索负责找到候选证据，模型负责生成和语义判断，确定性代码负责引用合法性、状态转移和持久化。接下来我会优先统一研究主路径里的证据保存和严格核验策略，再扩展更复杂的任务，而不是继续增加并列功能。

## 三 用一次请求讲清楚实现

### 演示问题

假设资料库有两份技术文档：文档 A 说明某虚构传感器使用 M7 控制器，文档 B 说明 M7 控制器支持 CAN 通信。问题是“该传感器通过哪种总线通信”。这个例子用于解释跨文档证据链，不是项目已经验证过的具体数据集记录。

### 从用户问题到研究结果

第一步，创建任务。任务目标写入 session。创建接口不自动完成任意目标拆解，也不自动建立完整 Goal 和 Subtask 图。

第二步，生成并激活研究计划。build_research_plan 生成 retrieve、draft、verify、repair 和 final_verify 等步骤；校验器检查引用、DAG 环、输入输出绑定、可执行判据、工具白名单等。保存计划与激活计划是两个动作，校验未通过的计划不能直接执行。

第三步，调度检索。PlanRunner 从持久化状态选择可运行步骤，ResearchStepExecutor 通过 ResearchTool 调用检索层。检索内部可以先检索原问题，再根据子问题寻找“传感器到控制器”和“控制器到总线”的证据。

第四步，保存并传递证据。主 DAG 中，工具结果进入 ToolCall.result，refs 进入 Attempt.output；data binding 将 refs 传给草稿、审核和终检。这一步有持久化，但不能把它说成所有证据都自动写入状态图。

第五步，写草稿。模型结合任务状态视图、问题和证据生成答案。当前 RAG 的基准生成提示偏短答案，研究流程可以围绕它继续生成草稿；完整长篇研究报告不是已经充分评测的能力。

第六步，审核和修订。审核者接收草稿及证据，返回 verdict 和 issues。有 issues 才进行改写，没有则复用原稿。Atlas 这一层是模型审核，不等价于检索层的 claim 引用编号校验。

第七步，终检和结束。终检 verdict 归一后得到 approved，程序用布尔判据决定是否通过。它保证遵守审核门槛，但并不把模型 verdict 升级成独立的事实真值。

第八步，处理中断。若步骤输出已经提交，后续从数据库读取；若工具调用仍在途或结果未知，恢复评估先阻止继续，待对账定论后再恢复允许推进的步骤。

### 三种图必须分清

| 图 | 节点或对象 | 回答的问题 | 代码位置 |
|---|---|---|---|
| 执行 DAG | Step 与 Dependency | 哪一步依赖哪一步，哪些输出传给下游 | atlas/planning |
| 研究状态图 | Goal Constraint Decision Fact Artifact 等 | 当前采用什么状态，来源和版本关系是什么 | atlas/memory |
| 检索实体图 | 实体 关系及 chunk 关联 | 哪些跨文档内容可以通过实体关联被召回 | compassrag/index/kg.py |

### 一页架构说明

```text
用户问题
  ↓
Atlas 任务接口和研究模板
  ↓
PlanRunner 读取步骤与依赖
  ├─ retrieve → ResearchTool → CompassRAG
  │                            BM25 和可选 dense
  │                            RRF 与可选多跳核验
  │                 ← 答案 证据 停止原因 trace
  ├─ draft → 问题 状态视图 证据 → 模型草稿
  ├─ verify → 草稿 证据 → verdict 和 issues
  ├─ repair → 有问题才改写
  └─ final_verify → approved → 步骤判据
       ↓
SQLite 保存计划 尝试 工具结果 checkpoint 和事件
       ↓
完成 或失败 或先对账再恢复
```

## 四 项目动机和架构追问

### Q01 你到底做了一个什么项目

我做的是研究型 RAG Agent。RAG 负责从资料库取证，Atlas 负责把检索、草稿、审核和修订组织成可以记录、检查和恢复的步骤。我的核心问题是答案依据是否清楚，以及中断后执行状态是否清楚。图记忆和多角色都是实现手段，不再作为彼此独立的项目目标。

### Q02 为什么做这个项目 它有什么使用场景

我选择的是需要核对多个资料片段的研究问答，例如技术资料核查、跨文档事实查询和形成有依据的短结论。这类任务既要求证据，也可能有多轮调用和中间结果。我用公开多跳问答和受控任务验证这些机制，目前没有把它包装成已有企业用户的生产研究平台。

### Q03 相比普通 RAG 你多做了什么

我增加了两层能力。一层是证据处理：查询增强、多跳、claim 核验和有限修复都可以单独开关和评估。另一层是执行管理：把研究步骤、依赖、工具调用和恢复条件持久化。这些机制提供可追踪性和故障处理能力，但是否提高最终答案正确率，需要用同条件端到端实验判断。

### Q04 为什么不直接让大模型读完整资料

如果资料少、任务短，全量上下文是合理基线，我不会为了架构而强行检索。资料增多之后，输入长度、费用和无关内容会增加，检索提供选择性访问。多步骤执行还有另一类问题：即使模型能读完资料，程序也需要保存进度、工具结果和中断状态，这部分不能只靠大上下文解决。

### Q05 为什么不微调模型

我的需求主要是访问可更新、有来源的外部资料，以及管理研究执行过程。微调更适合调整行为、格式或特定任务能力，不能自然提供最新证据和执行恢复。我优先选 RAG；如果以后发现稳定的领域理解或输出模式问题，再比较微调与提示、检索改进的成本。

### Q06 Atlas 和 CompassRAG 怎么分工 为什么这么分

Atlas 管任务级执行，CompassRAG 管一次知识获取。双方通过 ResearchRequest 和 ResearchResult 交换查询、预算、证据、停止原因和 trace。这个边界允许替换本地或 HTTP 检索实现，也避免工具自行决定整个任务完成。代价是协议转换和两边预算、失败语义需要仔细对齐。

### Q07 这是 Agent 还是 Workflow

Atlas 当前主研究路径更准确地说是带模型步骤和检索决策的持久化工作流：顶层 DAG 来自固定模板，检索内部可以由模型选择 single、multi 或 direct，以及是否继续检索。我不会把固定模板说成通用自主规划器。使用 Agent 这个产品名称时，也会主动说明自主性发生在哪一层。

### Q08 多智能体是几个独立模型吗

不是必须。Planner、Worker、Auditor 表示职责，同一个模型可以分别承担。固定 DAG 的顶层结构已经由模板给出，不需要额外模型规划调用；legacy 编排才有显式 Planner 调用。我更强调角色输入和持久化交接，而不是同时跑几个 Agent。角色分离增加成本，收益必须通过消融验证。

### Q09 技术栈是什么 为什么这样选

后端用 Python、FastAPI、Pydantic、SQLAlchemy 和 SQLite；检索使用 bm25s、BGE M3 的可选本地编码，以及 NumPy；框架部分有 LangGraph，前端是 React 和 TypeScript。选择这些工具是为了让接口、检索和状态保存方便组合。当前没有引入分布式数据库或向量服务来承担尚未验证的规模。

### Q10 为什么既有 legacy 又有 DAG

这是演进留下的两条路径。legacy_research_v1 是固定角色编排，plan_dag_v1 把步骤和依赖显式保存，便于恢复和查询。我主讲 DAG，把 legacy 当兼容和对照路径。当前证据入图、上下文和接口幂等在两条路径上还不完全一致，这也是后续收敛重点，不能用一条路径的能力替另一条背书。

## 五 RAG 检索基础和算法追问

### Q11 文档怎么进入系统

我有两类入口。基准数据经过统一段落格式构建 chunk；上传入口 IngestStore 支持 txt、md 和 json，再构建索引版本。当前上传后的服务加载主要是 BM25，dense 和实体图构建选项尚没有完整实现。我不能说已经支持 PDF OCR、复杂表格理解或上传后自动建立混合索引。

### Q12 怎么切分文档 为什么这样切

基准语料按段落、句子近似切分，默认 max_chars 为 1800，overlap 为 200，按字符而不是 token 控制。保留句子和少量重叠有助于减少证据在边界被切断。当前句界规则主要识别英文标点，长句也可能超过目标大小，因此中文和硬长度限制还需要改进。这些默认值是起点，不是实验得出的普遍最优参数。

### Q13 chunk 太大或太小有什么影响

太小容易丢上下文，尤其是实体指代和跨句关系；太大容易把不相关内容带入检索和生成，也增加编码和提示成本。我会固定题集比较不同大小和重叠量的 evidence recall、full hit、EM 或 F1、token 和延迟，同时观察答案所在位置是否被截断，不能只根据召回选参数。

### Q14 BM25 是什么 项目里怎么用

我使用 bm25s 建立关键词索引，文本包含标题和正文，因为标题通常含有关键实体。BM25 可以理解为 IDF、经过饱和处理的词频，以及文档长度归一的组合。词频再高，收益也会递减；过长文档不会仅靠出现更多词占优。我复用库实现，没有自行改写倒排索引或宣称自研搜索引擎。

### Q15 BM25 的公式和参数怎么解释

常见形式是对查询词求和：IDF(t) × tf(t,d) × (k1+1) / [tf(t,d)+k1×(1−b+b×|d|/avgdl)]。k1 控制词频饱和，b 控制长度归一程度。不同库的 IDF 变体可能不同，公式用来解释原理；项目构建默认参数由 bm25s 决定，我没有完成专门的 k1、b 调参实验。

### Q16 中文关键词检索做了吗

目前 BM25 路径使用库的英文分词及停用词配置，主要评测也是英文多跳数据集。我不能把它说成成熟中文检索。面向中文需要补分词或合适的字符级方案，并用中文资料验证专名、缩写、混合语言和粒度；不能因为 embedding 支持多语言，就认为整个混合检索链路都适配了中文。

### Q17 为什么选 BGE M3 用了它的哪些能力

项目选择 BGE M3 作为本地语义编码器，可通过 sentence transformers 加载。实际使用的是归一化的单向量稠密表示，没有启用它全部的稀疏或多向量能力。我把这个模型当已有实现选择，不会声称它在我的资料上优于所有替代模型；选型收益需要用相同检索集比较。

### Q18 向量存在哪里 用了 FAISS 吗

没有。离线向量按分片保存为 NumPy 文件，查询时加载矩阵，对归一化查询向量做点积并排序取 top k。因为向量已归一化，点积等于余弦相似度。这个实现直观，适合当前实验规模；扫描成本大约是 O(Nd)，当前排序还有额外开销，不能拿它宣称百万级低延迟检索。

### Q19 为什么没有用向量数据库

当前优先级是明确检索行为、做消融和控制依赖，本地矩阵足够说明问题。向量数据库会在增量更新、过滤、并发和规模上更有价值。如果扩大规模，我会比较 FAISS 或向量服务的 ANN 召回、延迟和运维成本。目前这是后续选择，不是已实现的生产架构。

### Q20 向量模型可以吃长文本 你的实现也一样吗

不能这样推断。当前 LocalDenseEmbedder 默认 max_length 为 512，虽然 BGE M3 模型有更长输入能力，我的封装仍可能截断超过这个长度的文本。chunk 又按字符切分，所以我会重点检查金标证据是否落在编码窗口外。改大长度或改为 token 切分，都需要重新评估成本和召回。

### Q21 为什么要混合检索

BM25 擅长专名、术语和精确匹配，dense 更能处理改述和语义相近表达。我希望两路互补，但混合不必然更好：如果某一路返回很多噪声，也可能挤掉另一条路径的好结果。所以我会看单路、混合和不同参数的同题集对照，不能只因为用了两种技术就声称效果提升。

### Q22 RRF 怎么做 为什么不用分数直接相加

RRF 按排名投票，score(d)=Σ w_i/(k+rank_i(d))，rank 从 1 开始，项目默认 k 为 60，权重默认相同。BM25 分数与余弦相似度不在同一尺度，直接相加不容易解释。RRF 避开分数标定，但会忽略原始分差；k=60 是基线选择，不能说是最优调参结果。

### Q23 给一个 RRF 的具体例子

假设 A 在 BM25 排第一，在 dense 排第三，等权且 k=60 时得分是 1/61+1/63。B 只在 BM25 排第二，得分是 1/62，A 更高。这个例子说明多路共同支持会加分。当前实现是在每条查询内融合检索器排名，多条查询之间再累积证据，不是把所有查询的所有候选做一次全局 RRF。

### Q24 去重 重排和 top k 怎么做

项目按 chunk_id 精确去重；当前近重合并还受 use_rewrite 开关和 dense 向量可用条件限制，按余弦阈值处理，默认阈值为 0.92，保留靠前证据。RRF 是排名融合，不是 cross encoder 重排器，项目也没有独立交叉编码 reranker。常见配置 top_k=10、max_evidence=20，但具体随配置变化。近重阈值也要防止把互补证据误合并。

### Q25 如何保证向量和 chunk 不错位

编码时按 chunks 顺序保存分片，加载时使用同源的 chunk_id 列表，并检查元数据的块数和分片行数。评测 manifest 还会记录语料与索引相关指纹。不过同样行数不意味着同样顺序，单靠数量检查不能完全防止错位。更严格的方案是在索引元数据里校验完整有序 ID 哈希和编码配置，这应当明确列为改进。

## 六 查询增强和多跳追问

### Q26 查询改写做了什么

查询增强提供问题分解和 HyDE 等变体，再用这些查询检索。原问题仍然有价值，不能被生成的改写完全替代。变体的作用是扩大相关证据覆盖；它们本身不是事实，也不能直接成为答案依据。最终仍要回到真实资料片段。

### Q27 HyDE 是什么 会不会把幻觉带进答案

HyDE 先让模型生成一个假设性答案或文档，用它作为检索查询，改善问题表述和资料表述不一致的情况。它可能生成错误内容，所以我只把它当查询线索，证据必须来自真实 chunk。如果错误假设持续把检索带偏，需要限制变体、保留原问题结果，并评估它的负例。

### Q28 single multi 和 direct 有什么区别

single 是单轮取证；multi 使用子问题队列和充分度判断，多轮补充证据；direct 则允许模型按自身知识作答。direct 是现有路由能力，但对必须有来源的研究任务，应当禁用或把无外部证据明确展示出来。当前不能声称所有配置都保证先检索后回答。

### Q29 多跳具体怎么执行

启用 decision 后，模型先产出路由和子问题。multi 路径先检索原问题，然后依次处理子问题或证据缺口，累积证据并检查是否充分，直到早停或轮数预算用尽。这是有上限的检索循环，不是无限自主思考，也不是 Atlas 自由生成任意执行 DAG。两种“规划”作用范围不同。

### Q30 怎么知道证据够了

充分度模型读取问题和已有证据，返回 sufficient 和下一条查询。它是模型判断，不能当作事实证明。当前解析失败会使用偏早停的降级值，并标记 parsed=False；因此我会把正常充分度早停与解析降级分开统计。严格研究模式应将后者转为未核验或人工复查，这还需要单独实现和验证。

### Q31 为什么还保留实体图

实体图用于补充跨文档关联信号。离线抽取实体和关系，把实体关联回 chunk，查询时以问题实体作为种子做 Personalized PageRank，再形成 chunk 排名，与其他检索路融合。它可以探索词面不重合的关联路径，但有抽取错误、建图费用和噪声扩散成本，所以是可选实验能力。

### Q32 PPR 原理是什么 为什么能找到多跳证据

PPR 可以理解为带重启的随机游走：p_next=αs+(1−α)Pᵀp，s 是查询相关实体的种子分布。分数沿图边传播，重启把游走拉回问题实体附近，因此可能触达相关文档。它得到的是相关性分数，不是对多跳推理的逻辑证明；图里的错误关系也会传播噪声。

### Q33 为什么不把实体图作为默认主线

基础 RAG 是否有效，应先由简单可解释的基线证明。实体图需要离线模型抽取和更多资源，某些问题上也可能引入噪声。我把它放在消融阶梯里，分别看证据召回、完整命中和答案指标，再判断成本是否合理。状态图是运行管理需要，实体图是召回增强选择，两者不能混为一谈。

## 七 证据和核验追问

### Q34 证据对象里保存什么

对外证据主要包含 source、chunk_id、quote、score、retriever 和 rank，用于定位资料和解释来源。ResearchResult 还带停止原因、轮数、confidence 和 trace_id。score 是检索信号，不是事实可信度；rank 是排序位置，不代表该证据已被模型正确理解。证据对象与内部完整检索 trace 也不是同一份数据。

### Q35 claim verifier 是怎么做的

它是答案生成后的独立模型调用，要求模型拆出最小 claims，并给出从 1 开始的证据编号和 supported 判断。代码再把编号映射成当前 evidence_ids：越界、引用不存在或声称支持却不给引用，都不能算支持。语义上是否蕴含仍由模型判断，代码不具备自动证明自然语言事实的能力。

### Q36 为什么单独调用 verifier 不一次生成答案和 claims

当前检索评测采用短答案口径，如果同时要求生成 claims 和引用，就会改变原答案协议，历史配置的 EM 和 F1 不容易继续比较。独立调用把生成和核验分开，便于消融与追踪。代价是额外延迟和 token，同一个模型也可能带有相关偏差，所以不能仅凭“第二次看了”就认为一定更可靠。

### Q37 核验有哪些失败类型 怎么修

诊断层区分 query miss、evidence gap、source conflict、unsupported 和 tool failure，规则将它们映射到有限动作，例如调整查询、补检索、重新作答或拒答。是否执行还受预算和 max_repairs 限制，默认最多一次修复。这不是无限迭代；失败分类的依据也含模型信号，必须看逐题 trace 才能判断归因是否合理。

### Q38 核验失败一定拒答吗

不能一概而论。启用核验且识别出证据问题后，流程可以有限修复，仍不支持时返回 unknown；但 verifier 默认关闭，而且解析全失败时当前只记录 parsed=False，不自动拒答。无证据时是否提前阻止生成也有独立开关。所以我不会说系统已经实现所有请求强制失败关闭，这正是严格模式要补齐的策略。

### Q39 Atlas Auditor 和 claim verifier 是同一件事吗

不是。CompassRAG verifier 面向一次检索答案，输出 claims 并执行引用编号校验。Atlas Auditor 面向研究草稿和约束，返回 verdict、issues，再由终检转换 approved。当前 Atlas 审核没有同等的确定性 claim 映射检查。Atlas 的 repair 主要接收草稿和 issues，没有显式绑定完整检索证据，也不自动触发顶层补检索；不能把两层修复能力混为一谈。两层可以配合，但也可能重复耗费资源，需要区分它们各自检测什么。

### Q40 两层核验看到的证据完全一致吗

当前不完全一致。检索内部可以使用最多 max_evidence 个完整块，常见配置为 20；ResearchResult 默认只返回前 5 条、每条约 280 字符的片段，Atlas 审核看到的是这个摘要协议。关键支持句可能位于片段之外。这是明确的接口损失，改进方向是按 claim 返回支持跨度或按 chunk_id 读取完整原文。

### Q41 引用有效就能保证没有幻觉吗

不能。有效引用只证明指向当前候选集合，不能证明其支持当前断言，更不能证明原资料在现实中正确。模型可能误读，资料可能过时或冲突。我的机制把引用错误和支持判断显式化，让它们可记录、可评估；可靠性仍然需要人工标注、冲突处理和严格策略验证。

### Q42 confidence 是怎么得到的

当前是启发式分数，综合返回证据数量、可用的 claim 支持情况和停止原因。它没有经过统计校准，所以 0.8 不意味着八成概率正确。我将它当作复核优先级信号，不当作完成判据或可信概率。后续如果要用于决策，需要标注集、可靠性曲线和校准检验。

### Q43 用户怎么看到来源 会生成标准引用吗

当前协议和 trace 能提供 source、chunk_id、quote，报告也可以展示证据来源。但不能把“有证据字段”等同于“最终答案每个句子都强制绑定且验证了引用”。检索基准答案还是偏短答。若要长报告，我需要增加 claim 到原文跨度的映射、渲染规则和覆盖率检查，这属于后续完善。

## 八 状态图和上下文追问

### Q44 状态图里存什么 为什么需要图

图节点有 Goal、Subtask、Constraint、Decision、Artifact 和 Fact，关系表达子任务、依赖、支持和替代等语义。图用于表示状态之间的来源和生命周期，便于知道哪条决定仍有效、旧产出被谁替代。不是所有任务都必须用图；简单问答可以只存结果，图的收益主要出现在状态有关系和变更的时候。

### Q45 你的状态图是知识图谱吗 为什么不用 Neo4j

它是研究执行相关的有类型状态结构，和检索实体图职责不同。当前关系规模和查询模式有限，节点与边可以存在关系表中，通过 Python 引擎操作，不需要为了“图”引入专用图数据库。若后续出现大规模复杂路径查询，再比较 Neo4j 等方案。当前没有图数据库上线经验可以宣称。

### Q46 为什么不能只保存聊天历史或摘要

聊天历史和摘要适合保留自然语言细节，但不方便稳定查询当前约束、被替代决定和证据关系。我把结构化状态作为可查询底座，同时保留摘要和近期原文补充细节。代价是抽取、schema 和治理复杂度，所以我不会声称结构化记忆在所有任务上都更省 token 或更准确。

### Q47 旧事实和旧决定怎么处理

旧节点通常保留，用 status、有效时间和 superseded_by 等信息表示失效或替代关系。上下文构建时过滤过期状态，对冲突和未验证内容留说明，而不是物理删除后丢失变更原因。系统可以确定显式状态是否有效，但不能自动保证任意两个自然语言事实的冲突都能被发现。

### Q48 所有检索结果都会写进图吗

没有。DAG retrieve 的证据主要保存在 ToolCall.result 和 Attempt.output.refs，通过 binding 传给下游；独立研究接口和 legacy 编排存在写 Fact 的路径。我会直接说明这个差异。接下来可以设计统一证据登记服务，但在真正接线和测试之前，不应该把它说成所有路径共享的现有能力。

### Q49 四区上下文具体是哪四区

分别是当前计划与约束、已完成工作摘要、近期原始记录、踩坑与提示。组装器优先保留当前状态，其余根据需求和配比裁剪，活跃约束和决定还有 ID 查账。默认剩余预算份额为摘要 30%、近期记录 55%、提示 15%，同时有最低预算。它是可解释规则，不是训练出来的最优分配策略。

### Q50 每次模型调用都严格限制在这个预算内吗

不能这样说。完整四区能力存在，但 API 构建路径通常只提供计划和提示，没有接入全部历史缓冲。ContextPackage 默认 4000 tokens，主要衡量状态视图；问题、证据和草稿还可能在外面拼进完整 prompt。旧记忆服务还用过 8000 预算，所以不能把某个数字说成全系统所有调用的硬上限。

### Q51 结转怎么做 会不会把模型猜测当事实

结转在子任务边界或上下文压力下提取候选状态，规则负责类型、引用和合法操作校验，模型负责语义提取。解析失败有有限重试与规则摘要降级，并保留降级标记。结构合法不等于语义真实，因此来源、置信度和待核验状态仍需要保存。结转主要来自原记忆服务，不是每个 API 都完整启用。

### Q52 ContextPackage 有什么用 是完整 prompt 备份吗

它记录上下文摘要指纹、区块 token、纳入和排除的引用及降级信息，帮助解释为什么某条状态被提供或过滤。目前持久化记录不包含完整正文，也不覆盖后来外拼的全部提示，所以不能说可以靠它逐字重建每次模型输入。完整 prompt 归档还需要单独考虑隐私、容量和版本。

## 九 执行 持久化和恢复追问

### Q53 研究计划怎么生成 怎么避免错误计划执行

build_research_plan 根据问题和开关生成固定 DAG。校验器检查 schema、引用、环、输入输出类型绑定、可执行判据、工具白名单、前置条件和预算等规则。计划通过校验再保存和激活。它阻止结构错误，并不证明计划一定能完成研究目标，更不等于已经实现通用模型任务分解。

### Q54 Step Attempt 和 Dependency 分别是什么

Step 表示计划中的逻辑工作，Attempt 保存一次具体尝试的输入输出、错误和状态；同一步可有多次尝试，历史不覆盖。Dependency 表示执行顺序或数据传递，data 边有 binding，例如把 retrieve 的 refs 绑定为 verify 的 evidence。恢复能按已提交输出继续，而不依赖进程内变量。

### Q55 怎么判断步骤完成 模型说完成就算吗

执行器产出候选 output，PlanRunner 再用 Criterion 求值。结构判据能查字段，证据判据能查引用数量，终检用 approved 布尔值。这样可以避免只有任意 verdict 字段就通过，但 approved 仍由模型审核归一得到。我区分协议完成和事实答对，后者需要独立 gold 或人工评价。

### Q56 为什么用数据库 为什么用 SQLite

任务要跨进程保存步骤、尝试和结果，内存字典无法提供这种能力。当前用 SQLAlchemy 和 SQLite，开发、演示和事务处理成本比较低。表结构尽量不依赖专有列类型，但没有完成 PostgreSQL 生产部署验证。我不把方言编译通过等同于真实迁移和并发测试通过。

### Q57 怎么保证写图和写事件一致

GraphRepository 是图写入入口，节点或关系与对应追加事件在一个数据库事务中提交，测试通过打断事件写入验证回滚。这个保证覆盖该事务边界，不能扩展成模型调用、远端工具和本地数据库的全局事务。外部调用需要另外使用意图记录、幂等、对账等协议。

### Q58 event checkpoint 和 trace 有什么区别

event 记录业务状态变更，checkpoint 保存任务状态及恢复所需摘要，trace 记录模型或工具执行过程和诊断信息。恢复以持久化业务状态和调用记录为准，不能仅靠日志猜测。当前事件 replay 主要用于审计和部分状态重建，不保证可以从事件完整还原数据库的每一张表。

### Q59 LangGraph 负责什么 为什么不全交给它

LangGraph 在现有检索和角色流程中表达控制流，没有被当成 Atlas 业务状态的第二个持久化真源。显式研究计划则由自有 PlanRunner 调度。这样我能统一步骤、事件和工具结果的查询与恢复，代价是需要自己实现更多状态和恢复逻辑。框架运行时有临时 state，并不等于业务数据库被替换。

### Q60 并发推进会不会执行两次

数据库里有条件 claim、工具键唯一约束，运行时也有一定进程内会话锁，用来降低重复推进。但这不是完整分布式执行系统。我还没有完成多实例调度、租约、崩溃接管和隔离级别的系统压力验证。回答时应说明具体操作由哪层保护，不能把一个内存锁称为跨进程锁。

### Q61 为什么超时不是确定失败

因为客户端没收到响应，不代表服务端没处理。请求可能在上游已经完成，只是返回丢了。如果直接重发，可能重复付费或重复产生副作用。所以我区分确定未生效、已生效、部分生效和未知。未知调用先进入对账流程；当前检索也采用较保守的冻结策略，虽然只读，但仍可能重复计算和付费。

### Q62 工具调用从发起到结束是怎样的

ToolDispatcher 先保存意图和稳定幂等键，再条件更新 claim、派发，最后结算结果。持久化成功结果可以复用；结果未知则保留 indeterminate 等状态，避免直接重新派发。工具能力显式声明是否支持幂等、查询结果和补偿，调度器据此判断能自动处理多少，没有能力时不能假装已对账。

### Q63 幂等键怎么生成 为什么不带重试次数

持久化 ToolCall 用工具、作用域和规范化参数生成稳定指纹，相同逻辑操作重试应复用同一键，若把 attempt 放进去会变成新操作。参数改变则应当改变逻辑键或明确报冲突。但 ResearchRequest 的默认键来自 session 和 subtask 等，是另一套历史机制，不能把 ToolCall 的保障套到所有入口上。

### Q64 缓存是不是幂等 整个系统会阻止同键不同问题吗

缓存是复用结果的手段，不能天然保证并发只执行一次、跨进程有效或输入语义一致。检索内部缓存把请求语义摘要纳入查找键，但这是不同语义分开缓存，不等于统一返回 409。Atlas 独立 research 接口也没有完整的请求语义冲突校验；我会把这是待统一的问题讲清楚，不宣称全系统已解决。

### Q65 怎么进行对账

工具支持按幂等键查询时，先查原请求结果；支持读回时可比对外部对象；都不支持或查询本身出错，就保持未知，交人工。查回结果必须落库，后续恢复才能复用。人工定论是明确操作，不是模型自行猜测外部世界。当前检索 ToolSpec 未声明自动 lookup，所以不能说所有检索超时都能自动查回。

### Q66 进程中断后到底怎么恢复

先读取 active plan、步骤和工具调用，评估是否有未定论调用或人工闸门。有未知调用先对账；允许继续时，复用已经提交的成功输出，只推进可运行步骤。当前 runner 有对 dispatched 步骤的恢复处理，但没有完整覆盖 running 或 verifying 等任意硬崩溃点。因此我的表述是覆盖已测试的恢复场景，不是任意时刻的透明容错。

### Q67 能保证 exactly once 吗

不能承诺端到端 exactly once。数据库唯一键和条件 claim 可以约束本地逻辑记录，远端是否重复执行还取决于其幂等或查回能力。网络和跨系统事务之间仍有不确定窗口。我提供的是稳定调用身份、结果复用和未知先对账，避免把无法确认的结果当成成功或失败。

### Q68 部分写入和上游变化怎么处理

外部写工具是扩展能力：部分生效时，工具支持补偿才执行新的补偿调用，并保留原调用历史；补偿成功也不代表原步骤成功。另有前置条件与局部失效机制，外部条件变化可以使相关已完成下游变 stale，记录原因并保留无关结果。这些体现运行时设计，不作为研究型 RAG 的首页主流程。

### Q69 超时线程取消和预算能严格控制费用吗

不能。线程等待超时不等于杀掉远端请求，底层可能继续执行；检索预算通常在调用完成后的节点边界根据 usage 检查，单次调用仍可能超预算。Atlas 部分 DAG 模型接口只接到了轮数，没有完整的 token 和费用用量。严格控制需要调用前预留、供应商限额和完整 usage 接线，现状还没有全部做到。

## 十 评测 取舍和压力追问

### Q70 怎么证明这个项目有效

我把验证拆成检索、作答核验和运行时三层。检索看召回和完整支持证据覆盖；作答看严格 EM、F1、支持率、拒答及误拒答；运行时看真实触发的故障、恢复、重复调用和状态一致性。最后再在相同模型、题集、语料和预算下做端到端比较。机制测试通过不能直接证明模型效果提升。

### Q71 用了哪些数据集 为什么选它们

仓库保留 HotpotQA、2Wiki 和 MuSiQue 等多跳问答的采样与语料构建。它们有答案和支持资料，适合观察是否找齐证据。检索历史实验以 MuSiQue 小样本为主，但从采样题 context 并集建语料是受控设置，不等于开放互联网检索，也不能直接引用为完整官方基准成绩。

### Q72 evidence recall 和 full hit 有什么区别

evidence recall 衡量所需支持证据被找回了多少，full hit 衡量一题需要的支持证据是否全部覆盖。多跳问题只找到一半资料，平均召回可能尚可，但答案依据不完整，因此需要 full hit。当前检索评测主要按支持文档标题集合计算，命中标题不代表找到了精确支持句，更不等价于语义蕴含。具体比较时还要说明支持证据粒度、分母和 k 的定义，不能混着比。

### Q73 为什么同时看 EM F1 和证据指标

严格 EM 对答案表面格式敏感，F1 对部分重合更宽容，证据指标衡量资料是否找到。它们回答不同问题：找齐资料可能仍答错，答案字符串正确也可能没有证据支持。宽松 EM 可以帮助诊断日期或别名，但不能看到严格分数不好就换一个更宽松口径当主成绩。

### Q74 verifier 会提高准确率吗

不一定。它可能纠正错误，也可能误拒答或让答案变长而影响严格 EM，还增加调用和 token。历史材料里就有这类负结果。我会用人工样本检查拒答是否合理，再看支持率和质量成本曲线。核验的目标是让证据问题显式可处理，不能预设它一定提高准确率。

### Q75 消融应该怎么安排

先有 BM25、dense 和混合基线，再分别加入 rewrite、KG、decision、verifier。比较时固定题目 ID、语料、模型、输出协议和预算，保存每题 trace，并做重复运行。还可以在同一题目上配对比较，避免样本不同造成假增益。模块越多越需要消融，不能只给一个全开配置。

### Q76 现在能报哪些数字

我可以明确报告本次本地后端测试为 953 通过、6 跳过，这是功能回归证据。仓库还有确定性故障评测和小样本真实模型记录，但历史检索表存在配置变动和待重跑说明；我不会未经逐题产物核对就背成简历收益。被撤回的旧 40 步成绩也不使用，避免混淆过期评测口径。

### Q77 30 个样本是否证明效果可靠

样本数达到 30 不是有效性的开关。即使报告不再标机制小样本，也仍要看题目独立性、场景代表性、对照和重复次数。自建任务的 20 个干净题答对，不能外推到复杂研究任务。Wilson 区间可以表达二项比例的不确定性，但不能修复题集偏差和不同故障队列混算。

### Q78 怎样优化延迟和费用

先用 trace 分解编码、检索、模型生成、充分度、核验和重试的耗时与用量。然后优先减少无收益的调用、限制改写和修复次数、复用已完成结果，必要时只对高风险答案核验。当前没有足够证据让我报一个生产 P95 或统一节省比例，优化前后需要按同配置重测。

### Q79 上线还缺什么

当前是个人项目和本地演示。生产化还需要认证、租户隔离、资料权限过滤、敏感信息治理、异步队列、多实例恢复、索引一致性、限流和监控。资料片段也可能包含 prompt injection，不能当系统指令执行。我知道这些边界，但不会把尚未实现的安全能力写成已交付成果。

### Q80 项目是不是过度设计 你会怎么简化

这是合理质疑。项目历史上把记忆、编排、恢复和检索都放在主位置，叙事和接线因此变复杂。我现在只保留一个产品主线：研究问题到可追踪答案。展示混合检索、证据处理和恢复三个点，legacy、复杂写工具和实体图作为对照或扩展。是否删除代码要看调用与测试，不会为了介绍简洁直接破坏兼容。

### Q81 如果只给你两周继续做什么

我先统一主 DAG 的证据登记和引用生命周期，再补严格核验模式：解析失败明确标未核验，证据不足时策略一致；然后完成完整 prompt 预算及恢复断点测试。最后跑一套固定、可复现的端到端对照。暂不增加新框架或第三种独立 Agent，因为现在更需要一致性和效果证据。

### Q82 个人贡献和创新点怎么回答

我会围绕自己真正能解释的模块回答：协议边界、研究步骤与绑定、证据核验、持久化调用和恢复评测。BM25、BGE M3、RRF、PPR 和 LangGraph 都是已有方法或工具，不说成原创算法。这个项目的价值在于工程组合、失败语义和验证，而不是论文式创新。若某段由工具辅助实现，我也应能解释设计、测试和限制，不能把不理解的代码当贡献。

## 十一 可以完整讲述的工程案例

### 案例一 审核者看不到证据却判答案没有依据

**口述答案。** 我遇到过一个流程错误：检索和草稿已经有依据，审核仍然判没出处，修订后反而把正确结论删掉。我先沿 DAG 的输入绑定检查，而不是调整审核 prompt，发现只把 draft 传给 verify，没有把检索 refs 传过去。模型没有收到证据，当然无法核对。修复是在 retrieve 到 verify 和 final_verify 之间增加 data binding，并在审核 prompt 渲染证据。这个案例让我认识到，模型问题要先排查实际输入，流程图上“前面检索过”不代表后面真的看到了。

**继续追问。** 现在是否完全解决？解决了证据完全缺席的问题，但协议还有前 5 条及片段截断，审核看到的内容仍可能少于检索内部使用的内容。我不会把一次接线修复说成端到端证据完整性已彻底解决。

### 案例二 工具已生效但客户端超时

**口述答案。** 我设计过一个可控的 HTTP 场景：服务端已写入对象，故意不及时返回，客户端收到超时。直接重试就可能重复写。我把调用过程拆成先落意图、派发、结算；超时落成未知，先根据幂等键查询原结果，查回成功结果后保存并复用。这个场景检查服务端实际写入次数，而不只看任务最后是不是 completed。它证明的是该工具声明能力下的恢复，不是所有外部系统都能做到。

**继续追问。** 上游没有查询接口呢？读回能证明就读回，证明不了就保持未知并要求人工。不能为了自动化而把不知道变成没发生。

### 案例三 空答案来自推理预算耗尽

**口述答案。** 历史检索评测有一批空答案，第一反应很容易是模型能力差。我检查 finish_reason 和 completion 用量，发现推理模型的思考与最终答案共用输出预算，预算耗尽时正文为空。现有实现保留更充足的首轮预算，空答案再按 2048、4096 等阶梯有限重试，并增加收尾提示。这里我更愿意讲诊断链路和回归测试，不把不同样本或不同协议的空答率直接对比成收益。

**继续追问。** 为什么不无限加预算？因为模型可能持续打转，增加成本和延迟。有限重试后要如实报告空答案或失败，不能无限等待。

### 案例四 声明了写前置条件却没有观测能力

**口述答案。** 工作区里有一项已存在的修复：计划要求“目标不存在才能写”，但工具没有 observe 能力时，旧逻辑相当于跳过检查。我把这类信息缺失理解为 unknown，而不是前置条件成立，步骤应进入 needs_human，不能派发写入。对应回归测试检查状态和实际请求数。这是运行时的三态原则：满足、不满足、无法判断必须分开。这个案例是仓库现有记录，不作为本次面试材料新增修复来介绍。

### 案例五 加核验后分数不一定上涨

**口述答案。** 历史材料里出现过加入核验后严格 EM 下降、token 增加的情况。我不会因此直接删掉核验，也不会换宽松指标掩盖。应该逐题区分正确纠错、合理拒答、误拒答和答案格式变化，再分别看事实质量与成本。这让我把核验定位成需要验证的质量策略，而不是一个默认提分组件。旧数字没有重新核对原始记录前，我只讲这个取舍，不背具体提升比例。

## 十二 模拟连续追问

### 追问链一 你说做了 RAG 到底用了什么

**面试官：用了向量数据库吗？**

我没有用。当前 dense 索引是 NumPy 向量分片和精确点积检索，BM25 是 bm25s。它满足实验规模，但扩展时需要 ANN 和更完整的索引服务。

**面试官：那你的技术难点在哪？**

不是封装一个向量库，而是让检索证据能进入多步骤流程，并明确核验、预算、结果未知和恢复的边界。比如我处理过审核步骤没收到证据的问题，这不是换个 embedding 模型能解决的。

**面试官：为什么又弄实体图？**

它是可选召回信号，用于研究跨文档实体关联，不是主流程成立的前提。我会用消融判断是否保留，而不是因为它听起来复杂就必须启用。

### 追问链二 你说可核验 是不是只是换个模型再问一次

**面试官：同一个模型会不会一起错？**

会。生成与核验的输入和任务不同，可以发现部分错误，但并不能消除相关偏差。所以我让代码检查引用合法性，把语义判断单独记录，并保留人工样本评价。

**面试官：代码怎么判断证据支持？**

代码目前只保证引用编号映射合法，不会自动证明语义蕴含。supported 的语义判断仍由模型给出，必须诚实区分。

**面试官：核验输出坏了怎么办？**

当前有有限解析重试，全部失败标 parsed=False，不强制拒答。对严格研究应用，我会将其改为明确未核验或阻止发布，并补测试；这是待完善策略，不会说成已实现。

### 追问链三 你说可恢复 为什么不直接重跑

**面试官：检索是只读 重跑有什么危险？**

只读确实少了业务副作用，但仍可能重复付费、耗时，结果也会变化。当前工具运行时偏保守，会冻结未知调用；未来可按纯本地检索和付费远端研究区分重试策略。

**面试官：保存 checkpoint 就够了吗？**

不够，还要看步骤输出是否提交，以及远端调用是否仍然未知。checkpoint 是摘要，恢复必须检查实际持久化表和工具记录。

**面试官：所有崩溃位置都支持吗？**

不支持。现有测试覆盖明确场景，running 和 verifying 等位置还缺统一接管协议。我会画出崩溃窗口，并补租约、状态修复和对应故障注入，而不是承诺万能恢复。

### 追问链四 为什么这么多模块 效果到底怎么样

**面试官：是不是堆技术？**

历史上范围确实扩得比较大。我现在按研究任务收敛，只介绍检索、证据和恢复，其他能力只在相关追问时展开。系统复杂度需要由场景和实验收益证明。

**面试官：有没有可靠的提升数字？**

目前我能直接确认的是功能回归和若干机制场景；历史真实模型结果需要核对固定题集、配置和逐题 trace 后再引用。我不拿测试通过率当作准确率，也不引用撤回的旧评测。

**面试官：如果效果没证明 为什么还有价值？**

工程价值是把调用身份、来源、状态和失败处理变成可检查对象，而不是仅返回一段文本。但它是否值得额外模型成本，仍需端到端对照验证，我会承认这部分工作还没完成。

## 十三 面试前核对清单

### 必须能画出的数据流

画出 Atlas 调 ResearchTool，返回 evidence 和 trace，证据进入 Step 输出，通过 binding 传给 draft、verify 和 final_verify；下面画数据库保存计划、尝试和工具调用。不要在没有接线证据时把每份检索结果都画成 Fact 入图。

### 必须能解释的参数

chunk 默认 1800 字符、重叠预算 200 字符；编码器默认 max_length=512；RRF 默认 k=60；近重默认阈值 0.92；常见 top_k=10 和 max_evidence=20；协议默认前 5 条证据、每条 280 字符；claim verifier 默认关闭；ContextPackage 默认状态视图预算 4000。它们属于不同层，不能混成一个统一配置，也不能说全部经过最优调参。

### 不要直接背的说法

不要说已消除幻觉、已完成通用自主规划、已支持百万级向量检索、所有上传文档都自动混合索引、所有证据自动入图、所有请求都严格核验、所有超时都能自动恢复、事件可重建完整数据库，或已完成生产多租户。

也不要说仅靠多 Agent、图结构或测试数量就证明效果。遇到没做过的追问，用“当前实现是什么、为什么先这样、限制是什么、下一步如何验证”四句话回答。

### 可用于简历的克制版本

围绕多步骤研究问答构建 Atlas RAG Agent，将 BM25 和可选 BGE M3 稠密检索、RRF 融合、证据核验与持久化研究步骤组合；实现 Step 输入输出绑定、工具调用记录及若干中断恢复场景，通过功能回归与故障注入区分检索质量、回答质量和运行时一致性。

这段强调已实现机制，没有预设效果数字。简历若加入实验收益，应补题集、样本量、模型、索引、预算、重复次数和可回溯运行记录。
