# CompassRAG 面试问答稿（基于 2026-10-28 的真实数字）

> 每条答案都能指到代码、决策卡或实验记录；**不确定的地方直说不确定**。
> 数字口径：MuSiQue dev 分层抽样 50 题、samples 小库 4,646 块、单次运行；严格 EM 为对外口径。

## 1. 为什么不是"检索一次再生成"？

多跳题的第二跳依赖第一跳的实体。固定单轮时，若第一轮没把第二跳的实体捞出来，模型只能拿残缺证据猜。
我的做法是把检索变成 Agent 的工具：先判难度（direct / single / multi），multi 时拆子问题逐轮查，
每轮后用充分度判定决定继续还是收手。实测 50 题里 35 题提前收手，平均 2.06 轮；
代价是 token 涨到 5.5 倍（2,162 → 11,935/题）。**收益我要如实说**：严格 EM 0.300 → 0.440（+14pp），
但证据召回反而从 0.720 掉到 0.523（逐轮累积、@10 只算第一轮的口径问题，我标注了）。

## 2. 三路检索各解决什么？为什么用 RRF？

BM25 管关键词精确匹配（人名、专名、数字），BGE-M3 稠密管语义相似（换了说法也能召），
实体关系图 + PPR 管跨文档关联（两跳之间往往靠共享实体连起来）。
三路 score 语义完全不同（BM25 原始分、余弦、PPR 分），**直接相加没有意义**，所以只用排名做 RRF；
近重再用向量余弦 ≥0.92 合并。消融上，实体图是唯一提升证据覆盖的一路：召回 0.720→0.813、
full-hit 0.460→0.600，而且最省 token（2,022/题）。

## 3. 核验怎么防止"模型说充分、其实没支撑"？

关键是**不让模型自己判引用合法性**：模型只负责把答案拆成 claims 并给出它认为的支撑编号；
编号是否越界、是否真在本次检索到的证据集合里、是否引空，**由代码判定**，任何一条不满足就记 unsupported。
在这之上才做五类失败分类和有限修复。实测 claim support 0.885；触发修复 10 次成功 4 次。
（实现见 `diagnose/verifier.py`，决策见 `D4`。）

## 4. 为什么预算要分四类？

因为没有一种预算能挡住所有浪费：轮数挡住"一直查"，token 挡住"每轮塞很多证据"，延迟挡住"接口慢"，
费用挡住"模型单价高"。四类都落成同一种可解释的停止原因（`budget_exhausted:{rounds,tokens,latency,cost}`），
评测里能按原因统计。实测 decision 行有 15/50 题是轮数触顶，说明预算确实在起作用而不是摆设。

## 5. 为什么答案协议不改，核验要单独调一次？

答案调用是 SQuAD 短答口径（"几个词"）。如果让同一次调用既出短答又出 claims 和引用，提示词和输出长度都变，
**历史消融表的 EM/F1 立刻不可比**（重跑一轮约 213 万 token）。所以核验是独立第二次调用，
只增加成本、不改变口径（`D4`）。代价是每题多一次调用——这也是核验行 token 涨 70% 的原因之一。

## 6. LangGraph 用来做什么？会不会变成隐藏状态源？

只做跳转：`plan → retrieve → verify → repair → answer → finish`，条件边表达 direct/single/multi/sufficient/
repair_required/budget。证据、工具调用、用量、停止原因全部记在 `AgentState`/`AnswerTrace`（项目自己的 schema），
框架状态里只有"下一步走哪条边"的标记（`D8`）。换掉框架不会丢业务事实——这也是我敢默认开启它的前提。

## 7. 你怎么证明重构没有偷偷改变行为？

不看单元测试绿不绿，用**旧实现做逐题对照**：从 git 取出重构前的模块，在真实索引上用假 LLM 跑同一批问题，
逐项比 evidence / rounds / queries / n_llm_calls / tokens；真 LLM 上再抽查两题比证据 id 与 prompt_tokens。
LangGraph 与顺序实现就是这样确认逐位一致的（`E2`）。单测只能证明"没坏"，这个方法才能证明"没变"。

## 8. 严格 EM 和宽松 EM 差 0.14–0.22，你怎么判断哪个对？

严格 EM 是对外可比口径（论文都用它），宽松口径只是**诊断**：金标 token 集合被预测包含即算命中。
差距的来源是模型答得太"完整"——`661` 写成 `661 CE`、`10 June 1819` 写成 `June 10, 1819`、
`Apple Corps` 写成 `Apple Corps Ltd.`。**两条都要报，但主数字只能用严格 EM**，宽松口径写进简历就是自欺（`D10`）。
它的真正用途是：判断一个模块"有没有用"之前，先看口径差异，别让度量替我做判断。

## 9. 你踩过最大的坑？

两次。一次是实体抽取超支：批准 3,815 块，实际跑了 20,287 块，超支约 946 万 token——根因是加变体参数时漏改了读语料那行硬编码。
修的时候没有只改那行，而是把语料、NER 缓存、finalize 过滤三处都改成由同一变体推导，并立了"批量 API 先报预算"的规矩。
另一次是网络：进程卡 20 分钟没有输出、CPU 0%，`lsof` 显示连着一个 Teredo IPv6 地址一直 SYN_SENT；
另有一个是把"模型已缓存"当成"不会联网"，SentenceTransformer 仍会做 hub 检查。两个都记成了经验卡。

## 10. 这个项目哪里还不够？

三条，都很具体：① **只有 MuSiQue 一个基准**，2wiki/hotpotqa 缺小库语料与实体图，三基准需要额外预算；
② **plan accuracy 只有弱代理**（路由 vs 跳数 0.980），没有人工标注的检索计划，所以"计划质量"其实没测；
③ **核验层的收益取决于口径**（严格 0.420 / 宽松 0.640），要让它真的提分，得先解决答案格式，实验已设计未跑。
